# Профиль пользователя

## Публичные интересы

`GET /users/{user_id}/interests` возвращает только списки публичных интересов:

```json
{"sport_ids": ["football"], "team_ids": ["cska"]}
```

Авторизация для чтения не требуется: этот контракт использует клиент
рекомендаций `news_svc`. Email и другие атрибуты пользователя в ответ не
попадают. У существующего пользователя без интересов оба списка пусты.
Неизвестный или отключённый пользователь получает 404.

`PUT /user/interests` с `Authorization: Bearer <access_token>` заменяет оба
списка у владельца токена. Тело имеет тот же формат; оба поля обязательны.
Пустой список очищает соответствующие интересы. В каждом списке максимум
100 строковых ID длиной 1–128 символов. Пробелы по краям удаляются, повторы
убираются с сохранением порядка. Неизвестные поля и некорректные значения
возвращают 422; запрос без токена — 401.

ID сохраняются как строки внешнего каталога; сервис не вызывает спортивный
каталог и не проверяет существование команды или вида спорта.

Интересы хранятся в атрибутах `sport_ids` и `team_ids` Keycloak. При записи
интересов и мягком удалении аккаунта остальные атрибуты сохраняются.

Новый realm получает декларации из `deploy/keycloak/realm-export.json`.
Для существующего realm `keycloak-sync` добавляет декларации в текущий
user profile на следующем цикле синхронизации, сохраняя другие атрибуты.
После обновления файлов пересоздайте `keycloak-sync`, чтобы подключился
новый read-only mount конфигурации:

```bash
docker compose -f deploy/docker-compose.yml up -d keycloak-sync
```

Дождитесь сообщения `user interest attributes synchronized`. API перечитывает
сохранённые интересы; если Keycloak отбросил значения из-за ещё не применённой
декларации, запись возвращает 502 вместо ложного подтверждения сохранения.

## Изменение профиля

`PATCH /user` с токеном владельца принимает `username` и/или `email`.
Конфликт имени или адреса возвращает 409, некорректные данные — 422,
отсутствующий пользователь — 404. Пустой объект не изменяет профиль.

Настройка realm `editUsernameAllowed=true` включена в конфигурации и
применяется `keycloak-sync` к существующему realm. После обновления сервиса
дождитесь цикла синхронизации перед переименованием.

При фактической смене email сервис сбрасывает подтверждение, добавляет
`VERIFY_EMAIL`, сохраняя другие обязательные действия, и отправляет письмо
на новый адрес. Ответ содержит поля профиля и `verification_sent`:

- `true` — письмо отправлено;
- `false` — адрес сохранён, но письмо отправить не удалось;
- `null` — email не изменялся и письмо не отправлялось.

Повторное сохранение прежнего email, включая различие только в регистре,
не сбрасывает подтверждение и не отправляет новое письмо. При ошибке
доставки можно повторно запросить письмо через `POST /send-verify`.
До завершения подтверждения нового адреса следующий вход может требовать
выполнить обязательное действие Keycloak.

## Активные сессии

Все маршруты требуют `Authorization: Bearer <access_token>` и работают
только с online-сессиями владельца токена.

`GET /user/sessions` возвращает список с полями:

```json
[
  {
    "id": "session-id",
    "started_at": "2026-11-09T10:00:00Z",
    "last_access_at": "2026-11-09T10:05:00Z",
    "ip_address": "127.0.0.1",
    "is_current": true
  }
]
```

Время возвращается в UTC. Список не содержит access- и refresh-токены.
Сессии других пользователей в него не попадают.

`DELETE /user/sessions/{session_id}` завершает одну свою сессию и возвращает
`200 {"status":"ok"}`. Перед удалением проверяется принадлежность сессии.
Чужой или отсутствующий ID получает одинаковый 404. Можно завершить текущую
сессию; следующий запрос с её токеном в `user_svc` получит 401.

`POST /logout-all` завершает все online-сессии текущего пользователя, включая
текущую, и возвращает `200 {"status":"ok"}`. Их refresh-токены больше не
обновляются; сессии других пользователей сохраняются.

Операции используют Keycloak Admin API и существующие роли сервисного
аккаунта; отдельная таблица сессий не создаётся. Offline-сессии в эти
операции не входят. Сторонние сервисы, которые проверяют JWT автономно,
не получают немедленный отзыв уже выданного access-токена через этот API.
