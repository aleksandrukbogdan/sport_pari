# Проверка доработок профиля

Проверки выполняются на собранном образе API с PostgreSQL и Keycloak 26.0
из текущего Compose. Для данных используется отдельный временный realm,
для почты — локальный Mailpit. Существующие пользователи и внешние почтовые
ящики не используются. Новые файлы тестов в репозиторий не добавляются.

## Интересы пользователя

Образ API: `sha256:d1226601eafd51c3cba0950d7a4ad5c6c4ca6c643dec6d4794d67b9b8d2ae47f`.

Проверены через HTTP к контейнеру API:

- пустые интересы существующего пользователя;
- запись, чтение, удаление дублей и пробелов, очистка обоих списков;
- 401 без токена, 422 для попытки передать чужой user_id;
- 422 для пустого ID, числа вместо строки, превышения 100 элементов;
- интересы другого пользователя не изменяются;
- ответ содержит только sport_ids и team_ids;
- 404 для отсутствующего и отключённого пользователя;
- сохранение других атрибутов при записи интересов и мягком удалении.

На realm без деклараций интересов проверены добавление деклараций через
`sync_user_profile`, сохранение стороннего атрибута и повторный вызов
без PUT к Keycloak.

Существующий набор: `python -m pytest tests -q` — **3 passed**.
`docker compose -f deploy/docker-compose.yml config --quiet` и
`git diff --check` завершились с кодом 0.

Временные контейнер API и realm удалены после проверки.

## Редактирование профиля

Образ API: `sha256:5231c2af11a9836c18e903bed76a60f109bbfa82b8efd91599f7129ee0728ec9`.

Проверены через HTTP к контейнеру API:

- пустой PATCH и email в другом регистре не меняют подтверждение и не
  создают письмо; verification_sent равен null;
- занятые имя и email дают 409, недопустимое имя — 422;
- смена email даёт is_verified=false и verification_sent=true;
- Mailpit получил письмо именно на новый адрес; переход по реальной ссылке
  подтвердил новый email, после чего выполнен вход;
- смена имени и вход с новым именем;
- при недоступном SMTP адрес сохраняется, verification_sent=false;
- другие обязательные действия и атрибуты сохраняются;
- повторное сохранение адреса после ошибки SMTP не вызывает повторную отправку.

Проверена миграция существующего realm с editUsernameAllowed=false на true,
включая повторную синхронизацию без PUT. Для режима с разрешённой сменой
имени повторены проверки интересов и мягкого удаления: Keycloak требует
передавать текущее username даже при изменении только атрибутов.

Существующий набор: `python -m pytest tests -q` — **3 passed**.
`git diff --check` завершился с кодом 0.
Временные контейнер API и realm удалены после проверки.

## Управление сессиями и итоговая проверка

Образ API: `sha256:eca6360ba64b3bb59c636ac0169f0f9ffb7fd308fe01ff3a4bd0229f6e2d3b57`.

Созданы две online-сессии одного пользователя и сессия другого.
Проверены через HTTP к контейнеру API:

- все три новых маршрута возвращают 401 без токена;
- список содержит только собственные сессии и ровно одну текущую;
- время начала и последней активности соответствует текущему времени
  и возвращается в UTC; токены в ответе отсутствуют;
- чужой и отсутствующий ID дают одинаковый 404;
- удаление выбранной сессии делает её access-токен неактивным для `/user`,
  а refresh возвращает 401;
- другая собственная сессия продолжает обновляться;
- logout-all делает access- и refresh-токены обеих оставшихся собственных
  сессий нерабочими для user_svc;
- сессия другого пользователя продолжает работать и обновляться;
- удаление текущей сессии завершает её, следующий запрос и refresh дают 401.

На этом же образе повторены все перечисленные выше сценарии интересов,
редактирования профиля, доставки и подтверждения нового email и отказа SMTP.
Существующий набор: `python -m pytest tests -q` — **3 passed за 6.47 с**.
Временные контейнер API и realm удалены после проверки.
